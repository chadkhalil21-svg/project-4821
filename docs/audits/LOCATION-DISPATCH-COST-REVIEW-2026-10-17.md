# Cost and location review: 17 October 2026

Status: review-only candidate. Production remains unchanged pending CI, Firebase/Stripe evidence and physical-device validation. This is **not** a measured capacity guarantee.

## Provider guidance consulted
- [Firestore pricing](https://firebase.google.com/docs/firestore/pricing): a successful document update is a write, and each listener observing an updated document can incur a read. Index-entry reads, Security Rules reads, minimum query charges and reconnections also matter.
- [Firestore Query Explain](https://firebase.google.com/docs/firestore/query-explain): measure the exact indexed query rather than assume cost from the number of operators.
- [Firestore vs Realtime Database](https://firebase.google.com/docs/database/rtdb-vs-firestore): Firestore remains authoritative for payments/compliance/trips; RTDB is an option for frequent live positions and connection presence **after** a separate budget, authenticated rule and physical-device experiment.
- [Stripe idempotency](https://docs.stripe.com/api/idempotent_requests): keys can be pruned after 24h; a repeat transfer after a successful-but-unrecorded transfer can move money twice.
- [Stripe transfer listing](https://docs.stripe.com/api/transfers/list): destination and transfer-group filters and pagination support reconciliation; absence of Firestore transferId **does not prove** no Stripe transfer.
- [Google SRE](https://sre.google/sre-book/handling-overload/) / [AWS Builders Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/): bound work, fail closed for ambiguous money, measure before scaling.

## Direct source evidence
1. `src/backend/telemetry.ts` previously wrote the parent `rides/{id}` doc on a maximum 15-second interval while moving: 100 writes / 25min, 240 writes / 60min per uninterrupted trip, plus each connected `onSnapshot` reading each changed doc. New conservative proposal samples locally on the same 15-second budget but publishes no more than once per 30 seconds moving, once per 60 seconds stopped: upper envelope 50 writes / 25min, 120 writes / 60min moving; 60/hour stationary. This **does not** suppress the first report, status changes, emergency escalation or server's one-minute monitoring cadence. GPS callbacks are not guaranteed by mobile OS; validate on physical devices and in traffic. Faster live map may later require a separate ephemeral live-location transport rather than lowering safety refresh.
2. `backend/geooperators.js` previously fetched overlapping pages 40 then 120 from every saturated geographic prefix. Candidate pool remains 120 per prefix, but second page now starts **after** the first document, fetching only 80 more. In a fully saturated two-tier/nine-cell scenario this avoids up to 720 repeated document reads per candidate search, 1,440 for two searches per booking, ignoring other indexed/billable work. Query minimums, index entries, and concurrency changes need live Query Explain.
3. `backend/server.js` still re-reads multiple account/operator documents during online renewal, and `src/backend/operatorInbox.ts` had an uncapped listener that initially downloaded historical operator rides. This PR restricts the active inbox to outstanding status with a 100-item saturation warning and adds an index declaration. Actual index commissioning is a separate launch gate; a dedicated paginated historical view remains separate. Also propose a separate safe security/cache review. No cut to emergency monitoring or insurance/Stripe validity without strict event/revocation proof.
4. `POST /operator/settle-pending` still reads all rides for an Operator and retries transfers without durable provider reconciliation. The periodic settlement path also needs atomic durable claims. **Do not deploy a superficial limit that hides real Operator debt**. Issue #55 remains P0. The required fix is a durable per-Travel payout ledger, backward-compatible exhaustive history census/backfill, source-of-truth Stripe transfer reconciliation (including old transfers without a transfer group), bounded pending work queue and controlled manual review of ambiguous states. No live money test performed.
